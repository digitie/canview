## Findings

### B-P1-01 — Observer plan staging이 만료되지 않아 영구적인 update DoS

위치: `shared/protocol/src/canview_uart.c`의 `plan_begin()`, `shared/protocol/include/canview_uart.h`의 plan state

`plan_begin()`은 pending candidate를 만들지만 timestamp, deadline, timeout 경로가 없다. 유효한 BEGIN만 보낸 뒤 CHUNK/COMMIT/ABORT를 보내지 않으면 pending 상태가 계속 유지된다.

재현 형태:

```text
plan_reset()
유효한 BEGIN(token=1) 전송
peer가 중단하거나 후속 packet을 보내지 않음
2초 이상 대기
새 BEGIN(token=2) 전송
=> CANVIEW_UART_PLAN_RESOURCE_BUSY
```

영향: active plan은 보존되지만 새 observer plan 갱신이 무기한 차단된다. 문서가 요구하는 2초 자동 폐기 조건을 만족하지 않는다.

권고: `pending_since/deadline`과 monotonic time을 추가하고 timeout·link/session 변경 시 candidate만 폐기한다. active plan은 유지해야 한다.

### B-P1-02 — Observer plan bandwidth budget이 검증되지 않음

위치: `shared/protocol/src/canview_uart.c`의 plan 상수와 `plan_begin()`

`max_records_per_second` 및 `max_bytes_per_second`에 대해 0, 과대값, 문서상 상한 초과를 거부하지 않는다. 값은 candidate와 active plan에 그대로 복사된다.

재현 형태:

```text
유효한 BEGIN이지만
max_records_per_second = 0 또는 65535
max_bytes_per_second = 0 또는 0xffffffff
```

영향: downstream이 해당 값을 실제 admission/bandwidth budget으로 사용할 경우 무제한 raw observer traffic 또는 queue/resource exhaustion이 가능하다. 문서의 1–200 records/s, 512–20,000 bytes/s 제한과 불일치한다.

권고: schema 또는 generated semantic validator에 경계를 넣고 state mutation 전에 reject한다. 0, min-1, min, max, max+1 시험을 추가한다.

### B-P1-03 — Command idempotency cache key가 replay/security context를 포함하지 않음

위치: `shared/protocol/include/canview_uart.h`의 cache key, `shared/protocol/src/canview_uart.c`의 cache lookup

cache key가 `request_token + command_id + canonical_digest`뿐이다. 문서가 요구하는 origin device, boot ID, wireless session, control generation, control tag가 없다.

재현 형태:

```text
session A에서 (token=T, command=C, digest=D) admit 및 result 저장
boot/session/control generation 변경
동일한 T/C/D로 새 요청
=> 이전 요청의 DUPLICATE/terminal result 반환
```

영향: 새 context의 정상 요청이 stale result로 처리되거나, 이전 context의 command identity가 재사용된다. `note_hello()`가 cache를 자동으로 epoch 분리하지도 않는다.

권고: 전체 context tuple을 cache key에 포함하거나 HELLO/session/generation 변경 시 cache epoch를 원자적으로 분리한다. reboot·session 재연결·origin 변경 replay 시험을 추가한다.

### B-P1-04 — Terminal result가 뒤늦은 결과로 덮어써질 수 있음

위치: `shared/protocol/src/canview_uart.c`의 `record_result()`

`record_result()`는 이미 terminal result가 저장된 entry인지 먼저 보호하지 않고 결과 payload와 terminal 상태를 갱신한다.

재현 형태:

```text
command admit
COMMAND_RESULT(COMPLETED) 저장
동일 command에 늦은 REJECTED/EXECUTING 또는 다른 terminal result 전달
lookup()
=> 마지막으로 덮어쓴 결과 반환
```

영향: result-before-ACK 및 duplicate command 처리에서 최종 결과의 불변성이 깨진다. controller가 재시도·실패 표시·감사 결과를 잘못 판단할 수 있다.

권고: terminal result는 immutable하게 유지하고 동일 canonical result만 idempotently 허용한다. 상태 단조성 및 delayed conflicting result 시험을 추가한다.

### B-P1-05 — HELLO/버전 협상 없이 ONLINE 및 command admission 가능

위치: `shared/protocol/src/canview_uart.c`의 `note_hello()`, `note_heartbeat()`, `command_admission_allowed()`

`note_hello()`는 nonzero peer boot ID만 확인하고 protocol range, selected version, capability, safety snapshot을 검증하지 않는다. 이후 matching heartbeat만 들어오면 ONLINE으로 전환될 수 있다.

재현 형태:

```text
link_reset()
note_hello(peer_boot_id)
note_heartbeat(same_boot_id)
tick(<300 ms)
=> ONLINE 및 command admission 허용
```

영향: 호환되지 않는 peer 또는 version skew 상태에서 command admission이 가능하다. 문서가 요구하는 HELLO_ACK, major match, capability/safety snapshot 조건을 state machine이 강제하지 않는다.

권고: 명시적인 negotiation state를 두고 validated selected version, capability, peer/local boot context, safety snapshot이 모두 완료된 뒤에만 ONLINE으로 전환한다.

### B-P1-06 — CTS 미확인 상태가 clear로 fail-open 처리됨

위치: `shared/protocol/src/canview_uart.c`의 `link_reset()`, `command_admission_allowed()`

`link_reset()`의 zero-initialization으로 `cts_blocked=false`가 된다. 첫 CTS sample 전에 HELLO와 heartbeat가 완료되면 CTS 상태가 확인되지 않았는데도 command admission이 허용된다.

재현 형태:

```text
link_reset()
note_hello()
note_heartbeat()
set_cts_blocked() 호출 없음
tick()
=> CTS blocked가 아니라고 간주되어 admission 가능
```

영향: reset 직후 실제 flow-control 상태가 확인되기 전에 command queue가 열릴 수 있다.

권고: `cts_known=false` 또는 초기 blocked 상태를 사용하고 정상 CTS sample 이후에만 admission을 허용한다. 실제 hardware pull-up과 software state를 HIL에서 함께 검증해야 한다.

### B-P1-07 — Plan revision 증가 및 commit digest가 검증되지 않음

위치: `shared/protocol/src/canview_uart.c`의 plan begin/commit

`plan_revision`이 active revision보다 큰지 검증하지 않고, `plan_digest`도 candidate의 실제 canonical digest인지 계산·비교하지 않는다.

재현 형태:

```text
active revision = 0
BEGIN revision = 0, expected_active_revision = 0
유효한 CHUNK 전송
임의의 32-byte digest로 COMMIT
=> revision 0 plan이 다시 active로 설치 가능
```

영향: stale/replayed plan이 optimistic concurrency 검사를 우회하고, digest가 plan 내용의 증거가 되지 않는다.

권고: 명시적인 strictly-increasing revision 정책과 wrap 처리, canonical candidate digest 계산·비교 후 atomic swap을 구현한다.

### B-P2-01 — Generated schema의 reserved/semantic 제약과 수동 codec 검증이 drift됨

위치: `shared/protocol/src/canview_uart.c`의 fixed payload validator, `protocol/schema/uart-v1.0.yaml`의 `CAN_CAPTURE_STATUS`

`CAN_CAPTURE_STATUS`는 generated policy상 fixed 44-byte message지만 수동 `validate_fixed_payload()`에 해당 reserved field 검증 branch가 없다. schema의 offset 40–43 reserved 값이 nonzero여도 CRC와 길이가 맞으면 통과한다.

또한 CAN_TX_AUDIT의 16-bit field가 `uint8_t`로 축소되어 high byte가 silently dropped된다는 의심이 있다.

재현 형태:

```text
정상 44-byte CAPTURE_STATUS 생성
payload[40..43] = 0x00000001
CRC 재계산
=> message_validate() 통과
```

영향: malformed/version-extension payload가 정상 status/audit 정보로 수용된다.

권고: reserved mask, enum, range 제약을 schema에서 생성하거나 중앙 validator로 통일하고 모든 reserved byte를 mutation하는 negative fixture를 추가한다. CAN_TX_AUDIT field width도 schema/generator/header를 대조한다.

### B-P1-08 — 3600초 fault-stream gate가 실제 C codec을 검증하지 않음

위치: `tests/protocol/uart_fault_stream.py`, root `CMakeLists.txt`

CTest의 `uart-fault-stream`은 virtual-time Python 모델 테스트다. `canview_uart_codec_feed()`에 random insert/delete/flip stream을 주입하는 C implementation test가 아니다.

영향: Python 모델과 C codec이 서로 다르게 regress해도 gate가 green일 수 있다. 현재 host C test는 제한된 malformed/oversize/CRC 시나리오만 검증하며 task의 24시간 C stream acceptance를 대체하지 못한다.

권고: compiled C codec에 deterministic mutation/fuzz stream을 직접 연결하고 long-run counter·buffer·resynchronization을 C 구현에서 검증한다. Python model test와 implementation test를 별도 gate로 구분한다.

### B-P3-01 — Command TTL 상수와 semantic source가 혼동되기 쉬움

위치: `shared/protocol/include/canview_uart.h`의 `CANVIEW_UART_COMMAND_TTL_MS`, `shared/protocol/src/canview_uart.c`의 cache retention

공개 매크로 `CANVIEW_UART_COMMAND_TTL_MS`는 60000 ms이지만 request TTL validator는 500–30000 ms이고 cache retention도 source의 hard-coded 60000 ms를 사용한다. schema에는 request TTL semantic min/max가 없다.

직접적인 P1 취약점은 아니지만 caller가 이 매크로를 request TTL로 오해할 수 있다.

권고: `CACHE_RETENTION_MS`로 이름을 분리하고 request TTL min/max를 schema/generated constants로 단일화한다.
