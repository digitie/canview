## 공격 시나리오와 판단

### 1. Prefix consumed·offset·마지막 chunk

위치: `receiver.c:56–67,75–90`, `envelope.c:prefix_feed`

31B 입력이 prefix 끝을 넘어가는 경우에도 caller는 요청량이 아니라 `consumed`만 offset에 더한다. prefix 뒤에 남은 바이트는 본문 처리에서 원본 offset으로 다시 읽는다. prefix 절단·오류가 발생하면 다음 검증 단계로 진행하지 않는다.

입력 총길이를 bundle 상한으로 제한한 뒤 offset을 `uint32_t`로 변환하며, 검토한 collector 계약에서 `consumed`는 요청량을 초과하지 않는다. 해당 조합에서 누락·중복 처리나 정수 wrap 경로는 확인하지 못했다.

### 2. 원본 불변성과 마지막 바이트 변이 수명

위치: `receiver.c:70,78–89`

서명 변이는 복사된 prefix에만 적용된다. 본문 변이는 마지막 바이트를 지역 `changed`에 복사해 적용한다. 남은 길이가 1보다 크면 먼저 마지막 바이트를 제외하고 공급하므로 zero-length feed나 마지막 바이트 건너뛰기가 발생하지 않는다.

`body_feed` 및 hash provider는 입력을 동기적으로 소비한다. `changed`의 주소가 호출 이후 보존되는 경로는 확인하지 못했다. embedded golden을 직접 수정하지 않는다.

### 3. Stage error와 잘못된 기대값에 의한 false PASS

위치: `receiver.c:50–96`

정상 입력의 `CANVIEW_OK`가 첫 필수 조건이며, 이후 세 변이에서만 `CANVIEW_AUTH_FAILED`를 기대한다. 각 단계는 이전 단계가 OK일 때만 실행한다. `body_finish`를 무조건 호출해 이전 오류를 덮는 경로가 없고, cleanup 실패도 최종 false로 처리한다.

다만 이 fixture는 최종 status 중심의 4-case 검사다. 모든 callback 횟수·오류 발생 단계·provider 고장 주입을 독립적으로 증명하는 oracle은 아니다. 검토한 현재 구현에서 구체적인 false PASS는 확인하지 못했으며, 이 제한을 전체 오류 경로 검증 완료로 확대하지 않는다.

### 4. Partial init·cleanup 실패 후 수명

위치: `receiver.c:30–47,95–99`, `body.c:232–257`, `ota_crypto.c`

PSA init 실패 시 close를 시도한다. body reset 실패 시 즉시 false를 반환하고 PSA context를 먼저 닫지 않는다. prefix/body/crypto가 정적 저장소에 있으므로 cleanup 실패로 남은 provider 참조가 지역 context를 가리키는 dangling reference로 바뀌지 않는다.

실패 시 자원이 남을 수 있지만, 이 fixture는 단일 task·단일 호출 계약이다. 이를 반복 호출 가능한 복구 API로 보거나 제품 자원 회수 완료로 해석해서는 안 된다.

### 5. Static one-shot·재진입

위치: `receiver.h:9–12`, `receiver.c:29–39`, `main.c:40`, `idf_receiver_host.c:17`

fixture 자체에는 mutex나 재진입 차단 상태가 없다. 대신 동시·재호출 금지 계약이 명시돼 있고 현재 두 caller는 한 번만 호출한다. 현재 연결에서 계약 위반을 확인하지 못했다. provider의 busy 방어를 fixture 전체의 동시성 보장으로 간주하지 않았다.

### 6. Stack·embed·component 소유권

위치: `receiver.c:30–39`, fixture `main/CMakeLists.txt:1–8`, `sdkconfig.defaults:1–7`

큰 prefix/body/crypto context는 정적 저장소다. SDK 입력은 embedded linker 구간을 사용하며 receiver가 전체 394KB golden을 stack에 복사하지 않는다. host driver의 파일 버퍼도 정적이다.

portable parser component 추가와 함께 기존 직접 `native_metadata.c` 등록을 제거해 해당 중복 편입을 피했다. host target은 별도의 CNG 분기로 동일 receiver를 컴파일하도록 연결돼 있다.

16KB main stack 예약과 개별 함수 frame 수치는 총 call-chain stack 여유의 증명이 아니다. SDK 내부 frame·heap·watchdog 시간·실제 section 배치는 이번 정적 리뷰에서 재측정하지 않았다. 문서도 이를 장치 검증 완료로 주장하지 않는다.

### 7. Host 파일 실패 및 권한 경계

위치: `idf_receiver_host.c:10–17`, `receiver.c:52–55`, `main.c:29–45`

host driver는 인자·open·read error·정확한 파일 길이·close 실패를 검사한다. 상한보다 한 바이트 큰 버퍼로 읽어 oversized 파일도 거절한다.
