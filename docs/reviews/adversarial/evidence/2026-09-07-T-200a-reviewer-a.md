- [app/main.c:34](F:/dev/canview-wt/t200a-review-a/firmware/communicator/esp32/app/main.c:34), 상세 설계 `core-bench.md:37` — 등록 이후 실패는 TWDT reset으로 이어진다는 계약.

**실패 시나리오**

기존 또는 변경된 실제 sdkconfig가 `CONFIG_ESP_TASK_WDT_PANIC=y`를 유지하면서 아래를 선택한다.

```text
CONFIG_ESP_SYSTEM_PANIC_PRINT_HALT=y
# CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT is not set
```

현재 gate는 이를 허용한다. 이후 main 진척이 중단되면 TWDT가 panic을 유발하지만, panic handler는 watchdog들을 비활성화하고 CPU를 정지시킬 수 있다. 문서화된 자동 reset 경로와 다르다.

**실행 근거**

Candidate의 독립 정상 fixture `SdkConfigTests.GOOD`에 위 설정을 추가하여 `GATE.validate()`를 실행했다. 추가로 PRINT_REBOOT와 `CONFIG_ESP_SYSTEM_PANIC_REBOOT_DELAY_SECONDS=99` 조합도 검사했다.

```text
ACCEPTED_BY_GATE: PRINT_HALT
ACCEPTED_BY_GATE: REBOOT_DELAY_99
```

SDK 원문에서도 확인했다.

- `components/esp_system/Kconfig:30` 이하: PRINT_HALT는 수동 reset이 필요한 선택지이며, reboot delay는 별도 설정이다.
- `components/esp_system/panic.c:452` 이하: halt 분기에서 `disable_all_wdts()` 후 halt 경로로 진입한다.
- TWDT의 `trigger_panic=true`는 이 최종 panic 정책을 강제로 reboot로 바꾸지 않는다.

**영향과 한계**

실제 설정 검사를 통과한 이미지라도 실패 후 자동 복구 동작이 계약과 달라질 수 있다. RUN_OK/TX 권한을 여는 결함은 아니므로 P2로 평가한다.

새 SDK 설정의 기본 panic 정책은 PRINT_REBOOT다. 따라서 **현재 candidate 바이너리가 HALT 설정으로 빌드되었다는 주장은 아니다.** 99초 설정 수용은 확인했지만, 실제 reset 지연을 계측한 것도 아니다.

**권고**

- 생성 defaults와 실제 sdkconfig gate에서 허용할 reboot 정책을 명시한다.
- HALT/GDBSTUB를 거부하고 reboot delay를 명시된 값으로 제한한다.
- 정상 fixture와 별개로 HALT, GDBSTUB, 비허용 delay 부정 시험을 추가한다.
- 수정 후 config gate와 실제 candidate SDK 빌드를 재검증한다.
