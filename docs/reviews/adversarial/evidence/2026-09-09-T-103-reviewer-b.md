**실패 시나리오:** analyzer가 중단되어 첫 summary만 남거나, 다른 실행의 fixture가 재사용되거나, TX 필드를 중복 키로 덮어쓴 로그를 수용한다. 누락을 “송신 없음”으로 판정한다.

**영향:** 필수 ACK/data TX 0건 gate의 검증 근거가 될 수 없는 입력에 성공 상태를 부여한다. 현재 physical gate를 미완료로 남긴 점과 별개로 checker 자체가 fail-closed 계약을 위반한다.

**권고:** canonical evidence schema와 중복 키 거부를 적용하고, 각 채널의 명시적인 TX/ACK 관찰 결과·완료 조건·실행 identity·sequence를 검증한다. 관찰 정보가 없으면 성공 대신 미실행/불충분 상태를 반환한다. 위 공격 입력을 독립 부정 fixture로 추가한다.

### B-P1-02 — 다채널 wrap 경계에서 정상적인 이전 epoch 프레임을 malformed로 버린다

- 위치: `firmware/communicator/stm32/module/fdcan_capture.c:253`
- 거부 분기: 같은 파일 `:255`–`:258`
- 호출 시 영향: 같은 파일 `:542`–`:548`
- 실제 발생 가능한 전달 순서: `firmware/communicator/stm32/platform/stm32g474/fdcan_capture.c:553`, `:564`
- 확인 방식: **후보 소스 분기 추적**. C 실행 재현은 수행하지 않았다.

다음 입력 순서를 추적했다.

1. channel 0의 source timestamp `0xFFFFFFF0`을 수용한다.
2. channel 0의 `0x00000010`을 수용하며 epoch를 증가시킨다.
3. channel 1 raw ring에 이미 대기하던 `0xFFFFFFF8`을 처리한다.

세 번째 입력은 최신 global source `0x10`보다 숫자가 크고 거리가 half-range보다 커서 `CANVIEW_MALFORMED`가 된다. 정상적인 이전 epoch의 cross-channel 지연 프레임인데도 malformed counter와 `BUS_FAULT`를 발생시킨다.

Platform worker가 channel 0의 raw ring부터 처리하므로 이 순서는 자연스럽게 발생할 수 있다. 기존 wrap 시험은 같은 채널의 wrap만 다룬다.

**영향:** 약 71.6분마다 발생하는 u32 timestamp wrap 근처에서 정상 캡처 데이터가 유실되고 잘못된 fault가 기록될 수 있다. 세 채널 ordering/보존 계약을 깨뜨린다.

**권고:** 인접 epoch의 지연 프레임을 구분할 수 있는 timestamp 확장을 사용한다. wrap 전·후 프레임이 세 채널에 교차 대기한 상태와 채널별 service 순서를 시험한다. 큰 forward jump 거부도 함께 유지해야 한다.

### B-P2-01 — 두 번째 이후 filter callback 재진입 시 이미 소비한 batch prefix가 사라진다

- 위치: `firmware/communicator/stm32/module/fdcan_capture.c:778`–`:782`
- 선행 소비: 같은 파일 `:816`–`:825`
- 시험 누락: `tests/stm32/test_fdcan_capture.c:512`–`:526`
- 확인 방식: **후보 소스 분기 추적**.

첫 번째 record는 ring에서 제거되고 inventory에 반영되지만 결과는 지역 변수 `result`에만 존재한다. 두 번째 record의 filter callback이 재진입하면 `batch`를 0으로 지우고 오류를 반환한다. 이미 제거한 첫 record는 복원되지 않으며 drop에도 포함되지 않는다.

**실패 시나리오:** record 두 개 이상을 넣고 첫 callback은 정상 반환, 두 번째 callback만 `build_batch()`에 재진입한다. 첫 record는 queue에도 반환 batch에도 없게 된다.

**영향:** guarded callback 실패에서 조용한 데이터 유실이 발생한다. 기존 시험은 첫 record에서 재진입하므로 이 경로를 검출하지 못한다.

**권고:** batch consumption을 transaction으로 만들거나, 실패 시 이미 완성한 prefix를 보존하는 명시적 반환 계약을 둔다. 재진입 위치를 첫 번째·중간·마지막 callback으로 바꾸는 시험을 추가한다.

### B-P2-02 — filter가 거부하는 프레임에는 worker 처리량 제한이 적용되지 않는다

- 위치: `firmware/communicator/stm32/module/fdcan_capture.c:766`, `:785`–`:796`
- 관련 공개 계약: `firmware/communicator/stm32/interface/canview_stm_fdcan_capture.h:7`, `:257`
- 확인 방식: **후보 소스 제어 흐름 검토**.

반복 조건은 출력 record 수가 12개 미만인지뿐이다. filter가 거부하면 `result.count`를 증가시키지 않고 계속한다. 문서화된 ISR producer 사용에서는 처리 중 새 프레임이 ring에 추가될 수 있으므로, 고정 ring 크기만으로 한 번의 worker 호출을 제한할 수 없다.

**실패 시나리오:** observer filter가 입력을 모두 거부하고 producer가 consumer 처리 중 계속 공급한다. 출력 수는 계속 0이어서 호출이 끝나지 않거나 과도하게 길어진다.

**영향:** observer 작업이 cooperative worker 예산을 잠식한다. 기본 app이 아직 adapter를 시작하지 않아 현재 image에서 직접 활성화되지는 않지만 공개 capture API의 bounded 계약에 결함이 있다.

**권고:** 출력 수와 별도로 방문/소비 record 수에 고정 budget을 둔다. filter 거부와 producer replenishment를 결합해 호출 종료와 후속 worker 진행을 검증한다.

**권고:** adapter register backend를 host에서 시험할 수 있게 하고 위 실패 경로를 실행한다. coverage manifest에 FDCAN module 및 적절한 adapter 범위를 명시적으로 추가한다. physical/HIL 검증은 계속 별도 유지한다.

### B-P2-04 — analyzer 입력 제한이 전체 파일 할당 이후 적용되고 일부 malformed 입력은 예외로 탈출한다

- 위치: `tests/hil/assert_no_tx.py:21`–`:25`, `:34`–`:36`
- 확인 방식: **후보 Python 직접 실행 및 메모리 read probe**.

`Path.read_bytes()`로 전체 파일을 먼저 읽은 뒤 8 MiB 제한을 확인한다. 따라서 대형 analyzer 로그가 이미 메모리를 소모한 후에야 거부된다. 메모리 할당 실패는 처리하지 않는다.


**영향:** bounded/fail-closed CLI라는 설명과 달리 대형 또는 비정상 evidence가 checker를 자원 고갈이나 traceback으로 종료시킨다.

**권고:** 스트림에서 최대 `MAX_EVIDENCE_BYTES + 1`만 읽고 제한한다. JSON parser의 숫자·깊이·비유한 값 정책과 예상되는 malformed 예외를 명시적으로 처리한다. 대형 실제 파일을 할당하지 않는 read-limit 시험도 추가한다.

## 공격했으나 새 finding으로 판정하지 않은 항목

- **Generated drift:** board manifest·pin source로 만든 header, defaults, partition 생성물 13개가 모두 일치했다.
- **Wrong SKU/PSRAM/ECC/GPIO:** 후보의 보드 부정 fixture와 generator 검증이 변조를 거부했다.
- **SDK 설정 우회:** 누락, 중복, malformed 값, unknown key, routing/HTTPD 설정, 금지 설정 삭제 변이가 해당 시험에서 검출됐다.
- **CMake dependency leakage:** STM32 module에 vendor header를 직접 넣은 변경은 없었다. ESP core의 C99와 SDK adapter component 경계도 이번 변경으로 바뀌지 않았다.
- **Build-mode 단일 flag 우회:** forced include, compile contract token과 mode override 거부가 유지된다. 새 source에서 차량 TX API 추가는 확인하지 못했다.
- **ISR에서 callback 실행:** 새 IRQ는 bounded FIFO snapshot을 수행하고 callback은 worker에서 호출한다. 실제 IRQ latency는 측정하지 않았다.
- **Target evidence의 이전 hash:** evidence가 가리키는 `b01831a43ae31d9ef2fc11bb382ef979d7115e6a`와 candidate 차이는 target evidence Markdown뿐이다. firmware/tools/tests/build 설정의 source drift는 없다. 따라서 hash 차이만으로 provenance finding을 만들지 않았다.
- **Warning policy:** 새 adapter가 strict project warning 옵션 대상에 포함된다. 실제 빌드 로그의 warning 0은 이번 실행에서 재검증하지 않았다.
- **Unsafe output path:** wrapper는 경로를 shell 문자열로 실행하지 않고 runner 인자로 전달한다. 기존 runner에는 symlink/junction 검사와 atomic report replacement가 있다. 실제 filesystem race 시험은 하지 않았다.
- **False physical/TX release 주장:** task와 target evidence는 physical/HIL을 미실행, 차량 TX를 NO-GO로 남긴다. 기본 app이 adapter를 시작하지 않는 것은 명시된 source-only 경계로 확인했다.
- **Secret 추가:** 읽은 변경 source와 fixture에서 실제 credential, provisioning key, VIN 또는 개인 capture 추가를 확인하지 못했다. 저장소 전체 과거 이력에 대한 secret scan은 수행하지 않았다.

```powershell
git cat-file -t $C
```

메모리 시험은 PowerShell here-string을 다음 명령으로 전달했다.

```powershell
$review | python -B -
```

실행한 Python 작업은 다음과 같다.

1. `subprocess.check_output(['git', 'show', C + ':' + path])`로 후보 source를 읽었다.
2. `types.ModuleType`과 `exec(compile(...))`로 generator와 SDK gate를 로드했다.
3. `Path.read_bytes/read_text`를 후보 객체 reader로 patch했다.
4. `generate_boards.outputs()`의 13개 반환 문자열을 해당 후보 객체와 비교했다.
5. 후보 SDK 시험 AST에서 파일 기반 `GATE`·`BOARDS` loader 할당만 제거하고 메모리 모듈을 주입했다.
6. 파일 생성 CLI 시험을 제외한 `SdkConfigTests` 12개를 `unittest.TextTestRunner`로 실행했다.
7. `assert_no_tx`에 `read_bytes()`만 제공하는 메모리 path double로 위 공격 입력을 전달했다.
8. wrapper의 `hil.run.main`을 인자 기록 stub으로 대체하고 기본 인자 및 `--channels 2`를 실행했다.
9. 메모리 고갈은 실제 대형 할당 대신 `read_bytes()` 진입과 `MemoryError` 전파를 보여 주는 probe로 확인했다.

## 미검토·미실행 범위

- C compiler/target build, ELF/MAP/HEX/BIN digest 재계산, warning 로그 직접 검증: **`NOT_RUN`**. Object-only 및 파일 비변경 제약을 유지했다.
- CTest, ASan/UBSan/TSan, coverage 수치 재측정: **`NOT_RUN`**. 기존 결과를 이번 reviewer 실행 결과로 인정하지 않았다.
- GitHub CI 실제 run 상태와 내려받은 artifact 검증: **`NOT_RUN`**. workflow와 기록된 evidence만 읽었다.
- SDK/vendor 원문과 silicon register 동작의 독립 재검증, IRQ W1C 동시 도착, 실제 memory-ordering 계측: **`NOT_RUN`**.
- 실제 board flash/boot, ST-LINK, GPIO/PHY/bitrate, IRQ latency, reset/brownout/rail, CAN analyzer ACK/TX 계측, physical HIL, 차량 CAN capture: **`NOT_RUN`**.
- Provisioning과 차량 TX qualification: **`NOT_RUN`**, 차량 CAN TX는 **`NO-GO`**.
- 생성물 정합성 확인은 pin/package의 전기적 적합성이나 제조 승인을 의미하지 않는다.
- 전체 저장소·전체 과거 이력 감사, KiCad/DBC/profile 실차 evidence 검증은 범위 밖이다.
