## 공격한 경로와 확인 근거

### 1. 사전 검증 전에 저장이 시작되는 경로

위치: `shared/ota/src/stage.c:28–55`, `body.c:62–85`, `manifest.c:370–504`, `floor.c:96–125`

서명·identity·길이·호환성·floor 또는 hash 시작이 실패했는데도 `storage.begin`이 호출되는 시나리오를 추적했다.

`stage_open`은 `body_open`의 OK 이후에만 storage 함수표를 복사하고 begin을 호출한다. body 내부에서도 preflight → floor → hash 시작 순서를 유지한다. begin 이전 실패는 stage FAILED로 전파되며 storage_live는 설정되지 않는다.

금지 target·중복 target·길이 합산은 `manifest.c:299–366`에서, 낮은 sequence와 같은 sequence/다른 digest는 `floor.c:68–93`에서 거절된다. stage가 이 판정을 우회하는 경로는 확인하지 못했다.

floor 성공 결과는 설치 승인이 아니다. ALREADY_INSTALLED/REPAIR_REQUIRED 구분과 freshness·실제 대상 보호는 후속 owner가 소비해야 하며 이번 stage가 이를 완료했다고 주장하지 않는다.

### 2. 거절된 chunk의 write 및 부분 처리 후 계속 진행

위치: `stage.c:59–75`, `body.c:119–184`

중복/hole·NULL·초과 chunk·padding/hash 오류 또는 image 경계를 넘는 chunk에서 일부 hash 처리가 진행된 뒤 실패하는 경로를 확인했다.

storage.write는 body_feed 전체가 OK인 경우에만 호출된다. body가 일부 offset/hash를 진행했더라도 오류 반환 시 해당 chunk 전체를 write하지 않으며 stage는 FAILED가 된다. 이후 feed/finish는 최초 stage 오류를 반환하고 저장/native callback을 다시 호출하지 않는다.

write 자체가 부분 작업 후 실패한 경우에도 재전송으로 이어가지 않고 reset을 요구한다. 이미 기록한 후보의 설치 금지는 provider 계약과 후속 owner 책임으로 남는다.

### 3. 미완료 body 또는 native 오류의 성공 오인

위치: `stage.c:78–93`, `body.c:204–229`

body_finish가 OK일 때만 storage.verify가 실행된다. native callback 오류는 FAILED로 전파되며 `NATIVE_MATCHED`는 성공 반환에만 설정된다. 성공 뒤 finish를 반복해도 native callback을 재실행하지 않는다.

`stage.h:15–19,31–43,85–93`은 저장된 native 전체 검증, 단일 owner, 설치/영속 상태 변경 금지를 분리한다. stage에는 PREPARED·selector·activation callback이 없다. 따라서 NATIVE_MATCHED를 실제 설치 승인으로 확대할 근거도 없다.

### 4. partial begin·cleanup 실패·최초 오류 보존

위치: `stage.c:15–19,49–51,96–115`, `body.c:6–36,232–256`

begin 호출 전에 storage_live를 설정하므로 partial begin 실패도 close 대상이다.

reset은 storage.close 성공 후 body.reset을 호출한다. close 실패 시 storage_live와 함수표/context를 유지한다. close 성공 후 hash cleanup만 실패하면 다음 reset에서 이미 성공한 close를 반복하지 않고 body cleanup을 재시도한다. 전체 정리가 성공하기 전에는 stage를 지우지 않는다.

이미 FAILED인 경우 stage_fail은 최초 작업 오류를 덮어쓰지 않는다. reset 반환값과 cleanup_error는 cleanup 실패를 별도로 전달한다.

이 판단은 `stage.h:40–43,65–66`의 **hash/storage context가 reset 성공까지 유효해야 한다는 계약**을 전제로 한다. storage.close가 아직 필요한 공용 hash context를 조기에 해제하는 provider는 허용되지 않는다.

### 5. 재진입·중첩·입력 수명

위치: `stage.c:6–12,28–44,62–68,80–85,98–104`, `stage.h:8–19,40–43,56–80`

모든 외부 callback 실행 동안 stage.busy가 유지된다. 동일 stage의 open/feed/finish/reset 재진입은 RESOURCE_BUSY로 반환되며 진행 상태를 변경하지 않는다. 이는 mutex가 아니고 단일 task 직렬화 계약이다.

stage와 고정 크기 입력 구조·prefix/chunk의 중첩 및 입력 주소 범위 wrap을 검사한다. opaque context는 주소 시작점만 검사하므로 **context 전체의 비중첩·유효 크기는 caller 계약**으로 남는다. 이를 임의 pointer 유효성 검증으로 해석하지 않았다.

prefix/chunk는 stage에 보존하지 않고 동기 callback 동안만 빌린다. DMA/queue에 pointer를 남기는 사용은 명시적으로 금지되어 있다.
