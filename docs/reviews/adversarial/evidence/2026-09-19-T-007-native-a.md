### A-NCLI-01 — ESP signature block의 scheme·내장 key 정합성을 검사하지 않아 native false PASS 가능

위치:

- `tools/ota/native.py:57–63`
- 성공 반환 경로: `tools/ota/native.py:64–71,139–142`
- 회귀시험 부족 위치: `tests/ota/test_native_container.py:66–77`

실패 시나리오:

1. 정상 RSA3072 서명 ESP image를 사용한다.
2. 마지막 4096B signature sector의 유효 block에서 다음 중 하나를 변경한다.
   - block version을 RSA `0x02`에서 ECDSA `0x03`으로 변경하되 SHA 선택 바이트는 0 유지.
   - 내장 RSA key material의 바이트를 변경한다.
3. 해당 block 앞 1196B에 대한 CRC32를 다시 계산해 block offset 1196에 기록한다. 원래 image 본문·RSA signature는 유지한다.
4. 변경된 전체 image의 outer hash를 갱신하고 유효한 outer manifest 서명을 제공한다.

정적 근거:

`_public()`은 제공된 PEM이 RSA3072인지 검사할 뿐, signature block의 scheme·내장 key와 연결하지 않는다. 호출하는 espsecure v5.4.0은 block CRC와 image digest를 검사하지만, RSA 검증 분기는 **외부 PEM의 key 종류**로 선택하며 block의 내장 RSA key material을 검증키로 사용하거나 PEM과 대조하지 않는다. 따라서 위 변경은 외부 PEM에 대한 RSA 검증 결과를 바꾸지 않는다. 이후 esptool의 image checksum/digest 및 CANView metadata도 그대로다. [공식 espsecure v5.4.0 source](https://github.com/espressif/esptool/blob/v5.4.0/espsecure/__init__.py)

반면 직접 읽은 ESP-IDF 고정 commit `76f5dedd9950a3012fee8fb7d5586df21fc67802`의 `secure_boot_signatures_app.c:35–43,249–276`은 scheme 일치와 block key digest의 신뢰값 일치를 요구한다. `secure_boot_rsa_signature.c:128–174`도 선택된 block의 key/signature를 사용한다.

영향:

장치 native 검증에서 거절될 block을 host가 `NATIVE_SIGNATURES_AND_METADATA_MATCHED`로 승인하고 조립 출력까지 생성할 수 있다. native 검증 도구의 계약 차이를 wrapper가 보완하지 않은 **host 검증 결함**이다.

이는 장치 서명 우회·Flash 쓰기·차량 안전 경계 붕괴를 입증한 것이 아니다. outer까지 유효한 입력이 전제이며 실제 재현 실행은 **NOT_RUN**이다.

권고:

- 성공으로 인정하는 **동일 signature block**에 대해 RSA scheme, 내장 key material과 외부 신뢰 공개키의 정합성, 실제 signature 검증을 결합한다.
- 고정 공식 helper/인코딩 계약을 재사용하고 새 암호 연산을 구현하지 않는다.
- block scheme 및 key material을 변경하고 CRC와 outer hash/signature를 갱신하는 회귀를 추가한다.
- 현재 `test_outer_valid_native_tamper`의 signature 바이트 변이는 CRC를 갱신하지 않아 이 경로를 검사하지 못한다.
