**B07-01 — P2: Explicit selection does not constrain FAIL result identities**

Location: [validate_evidence.py:415](F:/dev/canview-wt/t500-hil/tests/hil/validate_evidence.py:415), with inventory validation at lines 136–147 and 231–237.

The validator checks the inventory header against `expected_scenarios`, but compares actual result IDs with that selection only when the report status is PASS.

Reproduction performed:

1. Generate a valid full host report.
2. Change the first `stale-gates` event to `decision="ALLOW", vehicle_tx=True`.
3. Rewrite its JSONL through `EventLog`, updating byte counts and offsets, and recompute its FAIL analysis using the trusted scenario.
4. Retain only that `stale-gates` result.
5. Set the inventory header to `ids=["brownout"], count=1`.
6. Execute:

```powershell
python -B tests/hil/validate_evidence.py <temporary-output> --expect-status FAIL --expected-scenario brownout
```

Observed:

```text
exit=0
PASS evidence=... suite=host status=FAIL scenarios=1

```

A second variant retained a full 12-scenario inventory header but only one result. Validation with all 12 expected IDs also succeeded.

Impact: a caller receives successful evidence validation for an explicitly requested scenario that has no result. This does not turn FAIL into PASS, but breaks selection and completeness assurance.

Recommendation: whenever an explicit selection is supplied for a completed report, compare actual result IDs against it, regardless of PASS/FAIL status. Add missing-result and substituted-result FAIL regressions.

**B07-02 — P2: Runner-generated custom reports violate the structural-only contract**
