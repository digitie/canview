### P2 — B-NCLI-01: ESP 서명 block의 내부 key/scheme을 검증하지 않아 native 검사가 false-positive를 낼 수 있음

**위치**

- `tools/ota/native.py:57–71`, 특히 `:62`
- 성공 전파: `tools/ota/container.py:123–134`
- 회귀시험 공백: `tests/ota/test_native_container.py:66–77`

**근거**

`_esp()`는 외부 공개키가 RSA3072인지 검사한 뒤 `espsecure.verify_signature_v2()`를 호출한다. 그러나 이 공식 host 함수는 서명 block의 내장 RSA key 자료를 외부 공개키와 대조하지 않는다. RSA 분기에서는 block에서 signature를 추출하고, 호출자가 공급한 공개키로 검증한다. block 검사 또한 RSA/ECDSA 두 version을 허용한다. 따라서 공식 함수 호출 성공만으로 ESP32-S3 RSA profile 및 내장 key 일치가 입증되지는 않는다. 이는 공식 소스로부터의 정적 판단이다. [espsecure v5.4.0, 934–1065행](https://github.com/espressif/esptool/blob/v5.4.0/espsecure/__init__.py#L934-L1065)

반면 고정 ESP-IDF source `76f5dedd9950a3012fee8fb7d5586df21fc67802`의 `components/bootloader_support/src/secure_boot_v2/secure_boot_signatures_app.c:35–44, 91–110`은 설정된 scheme과 block version을 대조하고, block 내부 key로 검증한다. 현재 fixture도 `tests/fixtures/idf-ota-image/sdkconfig.defaults:6`에서 RSA scheme을 선택한다.

**실패 시나리오 — 실행 재현 NOT_RUN, 소스 경로로 도출**

1. 정상 ESP golden에서 `s = len(image) - 4096`으로 서명 sector 시작을 잡는다.
2. 유효한 첫 block의 내장 RSA modulus 바이트 `image[s+36]`를 변경한다.
3. 해당 block의 앞 1196바이트 CRC32를 다시 계산하여 `s+1196:s+1200`에 기록한다.
4. image 본문·기존 RSA signature·외부 trusted RSA 공개키는 유지한다.
5. 변경된 image의 outer SHA256과 manifest 서명을 갱신하여 outer-valid 컨테이너로 만든다.

공식 host verifier는 바뀐 내장 key를 사용하지 않으므로 기존 signature를 외부 공개키로 검증한다. image checksum/digest와 metadata도 변경되지 않았다. 현재 CLI는 이를 native 성공으로 표시하고 조립 출력을 생성할 수 있지만, target의 내장 key 검증·trusted digest 조건은 만족하지 않는다.

별도 변형으로 block version을 RSA `2`에서 ECDSA `3`으로 바꾸고 CRC를 갱신해도 외부 RSA 공개키 분기를 통과할 수 있다. target의 RSA scheme 검사는 이를 거부한다.

**영향**

장치가 거부할 잘못된 native artifact를 host가 `NATIVE_SIGNATURES_AND_METADATA_MATCHED`로 표시한다. 이는 일반 native 검사기·packager의 실질적 false-positive다. 장치 서명 검증 우회나 Flash 실행 성공을 주장하는 finding은 아니다.

현재 ESP 음성 시험은 payload 또는 signature 바이트를 변경하지만 block CRC를 복구하지 않는다. 특히 signature 변이는 CRC 단계에서 거절되어 이 공백을 드러내지 못한다.

**권고**

SDK helper를 재사용하여 **같은 signature block**에 대해 다음을 함께 확인하라.

- 요구된 RSA V2 scheme
- block 내부 공개키 자료와 외부 trusted root의 일치
- 그 block의 실제 RSA signature 검증 성공

한 block의 key 일치와 다른 block의 서명 성공을 조합해서는 안 된다. 내장 key 변경+CRC 복구, scheme 변경+CRC 복구의 outer-valid 음성 사례를 추가하고, CLI 실패 및 출력 미생성·기존 출력 보존을 확인하라. 자체 RSA 수학 구현은 필요 없다.
