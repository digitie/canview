**Findings**

**RA-01 — P1: CTS polarity is reversed**

Location: `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/platform/stm32g474/uart_dma.c:190`.

`cts_is_blocked()` returns true when PA0 is low. The board contract explicitly defines PA0 HIGH as flow stop; the adapter documentation also describes active-low CTS.

Failure scenario: a ready ESP32 drives RTS low. Hardware permits transmission, but software starts the blocked timer, inhibits admission after 100 ms, and invalidates the session after one second. Conversely, RTS high blocks hardware transmission while software reports CTS unblocked.

Impact: routine link operation repeatedly becomes suspect/offline, while real stalls bypass the intended software stall timers.

Recommendation: interpret PA0 high as blocked. Add adapter-level tests covering both levels, transitions, and the 100 ms/one-second boundaries.

Evidence: an in-memory source-checked truth table produced `LOW → blocked=true`, `HIGH → blocked=false`.

**RA-02 — P1: Session recovery invalidates a buffer still owned by TX DMA**

Locations:

- `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/module/uart_link.c:614`
- `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/module/uart_link.c:623`
- `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/platform/stm32g474/uart_dma.c:551`

`clear_local_session()` clears `tx_current` and zeroes `tx_serial`. It can run during inbound HELLO/heartbeat handling or maintenance. Those paths do not first abort the adapter’s active DMA transfer.

Failure scenario:

1. DMA is transmitting, or paused by hardware CTS, using `runtime->tx_serial`.
2. A peer boot change or session timeout invokes runtime recovery.
3. The runtime clears the DMA source and current-item metadata, while `platform->tx_in_flight` remains true.
4. When completion arrives, `canview_stm_uart_tx_finish()` rejects the missing current item with `CANVIEW_INVALID_ARGUMENT`.
5. The worker propagates that error; the scheduler faults and stops normal operation.

Impact: corrupted UART output, a stalled recovery path, or watchdog reset following an ordinary peer/session transition.

Recommendation: coordinate session invalidation with the adapter. Abort/quiesce TX before releasing its buffer, clear pending completion/error state, and associate completions with a transfer generation. Test peer reboot and heartbeat/CTS timeout while DMA is active and stalled.

The existing runtime lifecycle test manually finishes or resets borrowed buffers; it does not exercise this adapter/runtime interaction.

**RA-03 — P1: Boot-ID generation depends on an uninitialized RNG kernel clock**

Location: `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/platform/stm32g474/uart_dma.c:629`.

The new boot-ID function enables the RNG peripheral bus clock and RNG itself, then polls for data. The inspected startup path does not establish or verify its independent kernel clock. Searches found no `HSI48ON`, `HSI48RDY`, or `CLK48SEL` setup in the clock and UART adapter implementations.

Failure scenario: startup reaches this function with the RNG kernel source stopped. The bounded poll returns zero, and `app/main.c:50` treats that as a boot fault and waits for reset. Repeating the same initialization can repeat the failure.

Impact: the newly mandatory boot-ID dependency can prevent UART startup entirely.

Recommendation: explicitly configure and validate the RNG kernel source with bounded readiness/error handling before requesting entropy. Add a cold-start register test and failure-injection tests. Retain the existing refusal to substitute a predictable boot ID.

Evidence limitation: this is a startup dependency finding from source. The checked-in STM32 datasheet confirms the independent RNG clock/HSI48 relationship; actual reset-state and board behavior were not exercised. External vendor `SystemInit` source was outside the permitted worktree and was not inspected.

**RA-04 — P2: Time-sync rejects valid independent-clock offsets**

Location: `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/module/uart_link.c:1038`.

The COMMIT validator requires `t2 >= t1` and `t4 >= t3`, although `t1/t4` belong to the Controller clock and `t2/t3` to the STM32 clock.

Failure scenario: either MCU boots earlier, producing an ordinary positive or negative clock offset. A valid exchange fails these cross-clock ordering checks.

Two arithmetic examples were evaluated:

| `(t1, t2, t3, t4)` in µs | Offset | Network delay | Current ordering |
|---|---:|---:|---|
| `(1000000,1010100,1010110,1000210)` | +10,000 µs | 200 µs | Rejected |
| `(1000000,990100,990110,1000210)` | −10,000 µs | 200 µs | Rejected |

Impact: mapping establishment fails under normal independent uptime, preventing time-valid command admission.

Recommendation: validate ordering within each clock domain, then validate signed offset and round-trip calculations. Test positive/negative offsets, independent reboots, asymmetric delay, and wrap.

These examples evaluated the source’s arithmetic; they were not compiled-C executions.

**RA-05 — P2: Time-sync COMMIT is not bound to the complete, fresh local exchange**

Locations:

- `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/module/uart_link.c:1018`
- `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/module/uart_link.c:1034`
- `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/interface/canview_stm_uart.h:215`

Pending state retains token, boot ID, generation, and Controller `t1`. It retains neither the STM32 timestamps returned in the response nor an exchange expiration time.

Failure scenarios:

- A COMMIT supplies different `t2/t3` values from those generated locally; it can still create a valid mapping.
- A delayed old COMMIT receives a fresh `updated_ms` when accepted.
- A lost COMMIT leaves `pending_sync_valid` set indefinitely while normal heartbeats continue; a subsequent request with a new token/generation is permanently busy until session recovery.

The existing test at `tests/stm32/test_uart_link.c:1136` actually commits `t2=t3=6000` after the request response was generated at `5000`, and expects success.

Impact: incorrect or stale mapping can be marked fresh, and a lost exchange can block future synchronization. The current application’s NULL authorizer still prevents this from becoming vehicle command execution.

Recommendation: retain and validate the local response timestamps, impose an exchange deadline, and define retry/replacement behavior. Invalidate dependent pending work when its mapping identity becomes obsolete.

**RA-06 — P2: Safety inhibition does not inhibit command admission**

Locations:

- `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/module/uart_link.c:170`
- `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/module/uart_link.c:558`
- `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/module/uart_link.c:1170`

P0/P1 saturation and safety/control TX failures set `safety_inhibited`. Its only conditional reads are telemetry serialization; neither authorization nor admission checks it.

Failure scenario: a runtime with an authorizer encounters a P0/P1 overflow or failed control response. After one queue slot becomes available, another command can be admitted while the safety-inhibit latch remains set.

Impact: the documented fail-closed queue behavior is not enforced by the runtime. This is demonstrable for the supported authorizer configuration, although the shipped composition uses NULL and therefore denies commands.

Recommendation: enforce the latch at admission and executor-facing boundaries, with an explicit recovery policy. Test admission after saturation and after a failed P0 transfer, rather than checking only the counter.

**RA-07 — P2: The 64-bit millisecond API input still wraps after 49.7 days**

Location: `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/app/main.c:20`.

The worker widens the 32-bit `canview_stm_board_now_ms()` result to `uint64_t`; widening does not extend its epoch. The runtime expects monotonic 64-bit milliseconds, and its elapsed-time helper treats backward movement as `UINT64_MAX`.

Failure scenario: SysTick milliseconds wrap from `4294967295` to zero while the microsecond clock continues through its extended epoch.

Impact: session and mapping expiration decisions see a discontinuity, potentially invoking recovery and the active-DMA defect above. The wire command’s 32-bit issued milliseconds also lack an explicit wrap-extension policy.

Recommendation: derive runtime milliseconds from the same extended monotonic source or provide a proper millisecond extension. Define wire timestamp reconstruction separately.

This lies beyond the advertised 24-hour soak window, but violates the public monotonic-time contract.

**RA-08 — P2: DMA receive loss is discarded without useful loss accounting**

Locations:

- `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/platform/stm32g474/uart_dma.c:515`
- `F:/dev/canview-wt/2026-09-09-t104-review-a/firmware/communicator/stm32/platform/stm32g474/uart_dma.c:282`

When producer distance exceeds capacity, recovery clears the ring and resets both cursors. It does not record a DMA-overrun reason, unread bytes discarded, or a lower bound on overwritten bytes. Runtime `rx_oversize` counts codec failures, not this adapter loss.

Failure scenario: servicing falls behind an otherwise functioning DMA producer. Recovery succeeds and returns normal worker progress, with the evidence reduced to a generic link reset.

Impact: the acceptance requirement of no unaccounted byte loss cannot be evaluated from runtime diagnostics. Distinct UART faults and software backlog become indistinguishable.

Recommendation: preserve saturating adapter fault/drop counters across recovery, including discarded unread bytes and an explicit “unknown additional loss” indication when wrap accounting is uncertain.

**Attacked scenarios and residual uncertainty**

- **DMA cursor/wrap:** inspected CNDTR sampling, ISR wrap count, pending-wrap correction, 64-bit arithmetic, invalid CNDTR, and producer distance. The 64-bit cursor avoids ordinary 24-hour accumulation overflow. Multiple wraps with coalesced interrupts are not independently detectable from the current state.
- **Concurrent DMA writes:** the consumer checks producer distance once before parsing directly from the live ring. Buffer overwrite during parsing, including near-full conditions, remains unverified. CRC rejection is not a substitute for proving ownership or accounting for loss.
- **Singleton lifecycle:** start rejects another active adapter; stop rejects a different active owner; service reentry is guarded. No adapter-level behavioral tests were available. DMA-accessible address range and overlapping caller-owned objects are not validated beyond size/alignment.
- **Time extension:** TIM2 extension uses a PRIMASK critical section and documents a maximum sampling gap. The active worker calls it frequently. Multiple missed hardware wraps and saturation behavior were not exercised on hardware.
- **Reset/IRQ/TX:** inspected shutdown, event capture, recovery, pending IRQ handling, DMA completion and runtime borrowing. DMA completion versus final UART wire completion, CTS-stalled abort behavior, and line resynchronization remain physical verification items.
- **Watchdog/brownout:** startup and worker failures lead to fault/reset behavior; scheduler votes are bounded by time checks. Successful UART service does not itself prove physical RX/TX progress. External pulls, gate behavior, rails, and reset sequencing remain essential.
- **Bounds:** inspected fixed queues, 8 pending commands, 256 cache entries, payload copies, cache generations, and ESP pool owner/generation checks. No target ELF/MAP size or cumulative stack proof was independently produced.
- **Callbacks:** most mutating runtime APIs reject callback reentry. Initialization has no live-context guard, but its documented input is zero-initialized storage; calling it on an active context remains an unsupported-use hazard, not a separate finding here.
- **Fail-open behavior:** NULL authorizer denies control in the actual STM32 application. Lease acquisition is disabled by the capture-only compile contract. RA-06 affects configurations with an authorizer.
- **Communicator/Bridge isolation:** ESP preflight compares board profiles before GPIO/runtime initialization. The inspected Bridge BSP has no Communicator UART/control GPIO setup. ESP startup remains a health foundation, so end-to-end UART integration was not demonstrated.
- **Vehicle CAN TX:** no hidden vehicle-TX path was established in the inspected composition. Forced capture-only definitions, safe GPIO outputs, and the source TX scanner support this limited conclusion. It is not electrical proof.
