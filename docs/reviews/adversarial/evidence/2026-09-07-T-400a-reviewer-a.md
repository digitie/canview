### P1

#### T400A-A-001 — `runtime_open` 실패 시 board safe GPIO가 실행되지 않음

- 위치: `firmware/app/esp_core.c:12-17,26-43`
- 관련 위치: `firmware/platform/esp32s3/core_runtime.c:210-252`
- 재현:
  1. `canview_esp_board_runtime()`이 잘못된 pin, zero memory, invalid owner 또는 tick 설정으로 실패하게 한다.
  2. `app_main()`은 `canview_esp_core_boot()`을 건너뛴다.
  3. `safe_gpio`는 core boot 내부에서만 호출되므로 실행되지 않는다.
  4. 이후 `board.idle()`만 무한 호출한다.
- 영향: Communicator의 `RUN_OK`, recovery, RTS, TX 관련 출력이 소프트웨어로 safe state에 설정되지 않은 채 reset/default/tri-state 상태로 남을 수 있다. 외부 gate와 pull이 항상 안전하다는 가정에 의존하며, 해당 전기적 조건은 검증되지 않았다. 현재 candidate에서 직접 CAN frame 송신은 확인되지 않았지만 차량 송신 권한 경계에 연결된 fail-open 위험이다.
- 권고: `runtime_open` 전에 보드 safe state를 먼저 설정·검증하고, 모든 pre-core 실패 경로에서도 safe state가 보장되게 한다. open 실패를 검증하는 테스트에서 safe GPIO 호출 여부도 확인해야 한다.
- 심각도: P1

### P2

#### T400A-A-002 — watchdog feed timestamp가 실제 `esp_task_wdt_reset()` 전 시간임

- 위치: `firmware/platform/esp32s3/core_runtime.c:129-156`
- 관련 위치: `firmware/module/esp_core/health.c:147-161`
- 재현: `esp_task_wdt_reset()`이 SDK lock, cache stall 또는 기타 지연으로 deadline보다 늦게 반환하도록 만든다. adapter는 reset 호출 전에 얻은 timestamp를 `fed_at`으로 기록하고, core는 이를 유효한 feed로 승인한다.
- 영향: 20 ms budget과 watchdog deadline을 실제 reset 지연이 초과해도 정상 progress/feed로 기록된다. watchdog latency 보장이 코드상 성립하지 않는다.
- 권고: reset 호출 후 시간을 다시 측정하고, 호출 후 timestamp를 검증한다. 지연 또는 측정 불확실성은 terminal fault 및 no-feed로 처리한다.
- 심각도: P2

#### T400A-A-003 — watchdog 초기화 후 task 등록 실패 시 watchdog 없는 영구 safe-idle 가능

- 위치: `firmware/platform/esp32s3/core_runtime.c:53-70`
- 관련 위치: `firmware/app/esp_core.c:26-43`
- 재현: `esp_task_wdt_status()`가 미초기화 상태를 반환하고, `esp_task_wdt_init()`은 성공하지만 `esp_task_wdt_add(NULL)`이 실패하도록 한다.
- 영향: `watchdog_ready`는 false로 남고 core는 fault가 된다. 앱은 idle loop에 들어가지만 현재 task가 watchdog에 등록되었다는 보장이 없다. 부분 초기화된 전역 watchdog 상태도 정리되지 않는다.
- 권고: 초기화 소유권을 기록하고 task 등록 실패 시 복구/정리하거나 명시적 reset 경로를 사용한다. init 성공/add 실패 조합에 대한 회귀시험을 추가한다.
- 심각도: P2

#### T400A-A-004 — sample 실패 후 이전 정상 sample을 현재 값처럼 report함

- 위치: `firmware/module/esp_core/health.c:126-132`
- 관련 위치: `firmware/platform/esp32s3/core_runtime.c:189-207`
- 재현: 정상 boot/step 후 다음 sample에서 memory 또는 GPIO 오류를 반환한다. local sample은 폐기되지만 `core->sample`은 이전 정상 값으로 남는다. report는 stale 표시 없이 해당 값을 로그한다.
- 영향: Diagnostic Bridge evidence 및 진단 로그의 시간적 무결성이 깨진다. fault/status는 별도 로그에 있으나 개별 sample 필드가 stale인지 식별할 수 없다.
- 권고: sample validity, sequence 또는 timestamp를 저장하고 실패 시 sample을 invalid/stale로 표시하거나 값을 지운다. report는 유효한 snapshot만 정상 값으로 표시한다.
- 심각도: P2

#### T400A-A-005 — runtime board identity/profile이 generic memory와 pin 검증에만 의존함

- 위치: `firmware/platform/esp32s3/core_runtime.c:210-252`
- 관련 위치: `firmware/communicator/esp32/bsp/runtime.c:1-16`, `firmware/diagnostic-bridge/bsp/runtime.c:1-16`
- 재현: Communicator 하드웨어에 Diagnostic Bridge BSP를 링크하거나 반대로 한다. 양쪽의 pin은 SoC-valid이고 memory 값도 nonzero이므로 `runtime_open()`은 통과한다. 이후 잘못된 safe GPIO가 실행되고 sample 단계에서만 memory mismatch가 발견된다.
- 영향: 잘못된 board contract가 safe-state 적용 전에 또는 잘못된 safe-state 적용 후에야 감지된다. 외부 gate/pull이 안전하다는 하드웨어 가정에 의존한다.
- 권고: generated board ID/profile hash와 pin/memory contract를 compile-time 및 runtime port에 함께 바인딩하고, wrong-BSP 조합을 명시적으로 거부하는 테스트를 추가한다.
- 심각도: P2

#### T400A-A-006 — callback stage 및 ISR 호출 금지가 runtime 코드에서 강제되지 않음

- 위치: `firmware/platform/esp32s3/core_runtime.c:25-38,40-70,89-155,170-186`
- 관련 위치: `firmware/interface/canview_esp_runtime.h:33-57`
- 재현: 같은 owner task가 `safe_gpio` 전에 공개된 `watchdog_start`, `sample`, `feed`, `wait` callback을 직접 호출한다. 또는 해당 task를 중단한 ISR에서 callback을 호출한다. `owned()`는 task handle만 확인하며 safe-stage 또는 ISR-context를 확인하지 않는다.
- 영향: safe GPIO 이전 watchdog/sample 실행, ISR에서 heap/FreeRTOS blocking 또는 task-only API 호출, callback reentry가 가능하다. 현재 candidate 경로에는 ISR이 연결되지 않았으므로 현재 직접 발생 경로는 확인되지 않았다.
- 권고: stage latch를 추가해 callback별 선행 상태를 강제하고, ISR context를 명시적으로 거부한다. 가능하면 callback port를 외부에 노출하지 않는 opaque/private API로 제한한다.
- 심각도: P2

## 공격 시나리오별 결과

- null/zero/max: core, pool, runtime의 null/zero 검증과 pool generation max retirement 로직을 읽었다. 관련 host 테스트는 존재하지만 실행하지 않았다.
- malformed/truncation/version: 이번 diff에는 wire parser나 transport 입력이 없다. 해당 경로의 동작을 PASS로 주장하지 않는다.
- duplicate/replay: pool owner/generation/stale/double-release 방어가 있다. reset 후 token persistence나 reinitialization은 지원 계약 밖이다.
- timeout/deadline/budget: 경계 검사가 존재하나 watchdog 실제 호출 latency는 T400A-A-002로 남아 있다.
- queue/pool exhaustion: 고정 16-slot pool은 exhaustion을 반환한다. 실제 lock/critical-section WCET은 측정하지 않았다.
- callback lifetime/reentry: core busy guard는 있으나 runtime stage/ISR enforcement는 T400A-A-006으로 남아 있다.
- partial init: watchdog 부분 초기화는 T400A-A-003, pre-core safe GPIO 누락은 T400A-A-001이다.
- invalid board/sdkconfig: generator/checker 정적 검사는 읽었으나 실제 configure/build는 실행하지 않았다. board identity gap은 T400A-A-005다.
- dependency leakage/isolation: 정적 범위에서 common core에 vendor API가 없고 Diagnostic Bridge에 CAN, raw replay, ESP-NOW, UART, HTTP 송신 경로가 보이지 않았다. 빌드·링크는 실행하지 않았다.
- evidence integrity: stale sample 문제는 T400A-A-004다.
