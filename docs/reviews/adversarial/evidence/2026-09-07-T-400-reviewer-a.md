### P1 — merge blocker

**A-P1-01: wrong-BSP profile check occurs after an untrusted BSP safe-GPIO call.**

- Location: `firmware/app/esp_core.c:12,22,26`
- Failure scenario: a Communicator runtime object is linked with the Bridge board object, or vice versa. `app_main()` obtains that wrong `canview_board_port()` and calls `board.enter_safe_state()` at line 22 before `canview_esp_board_runtime()` reaches its profile comparison. The profile check itself is only in the BSP runtime at `firmware/communicator/esp32/bsp/runtime.c:9-13` / `firmware/diagnostic-bridge/bsp/runtime.c:9-13`.
- Impact: the mismatched board’s GPIO sequence is applied before rejection. For example, the Bridge sequence only operates GPIO 5 and 4 (`firmware/diagnostic-bridge/bsp/board.c:10-12`), while the Communicator safety sequence must first drive RUN_OK and multiple STM/GPS/UART-related outputs (`firmware/communicator/esp32/bsp/board.c:16-35`). Thus a wrong-BSP image can fail after performing an inappropriate hardware operation, rather than fail closed before any BSP action.
- Evidence gap: `tests/esp_core/test_wrong_bsp.c:43-44` invokes only `canview_esp_board_runtime()`. Root CMake’s cross-link targets likewise omit `firmware/app/esp_core.c` (`CMakeLists.txt:84-99`).
- Recommendation: validate `board.board_profile` against the compile-time expected profile before *any* `board.enter_safe_state`, `idle`, or other board callback in `app_main`; add full app+BSP cross-link tests asserting zero GPIO calls and zero runtime-open calls on both mismatch directions.

### P2

**A-P2-01: runtime open violates its documented ISR rejection contract.**

- Location: `firmware/platform/esp32s3/core_runtime.c:281-320`
- Failure scenario: `canview_esp_runtime_open()` or the BSP wrapper is invoked from ISR context with otherwise valid arguments. The function does not query `xPortInIsrContext()`, calls task APIs at lines 305-312, and persists `owner`, `wake_tick`, `initialized`, and callbacks.
- Impact: an ISR can bind the interrupted task as owner and consume the one-time runtime initialization. Subsequent normal startup receives `CANVIEW_RESOURCE_BUSY`; this is a fail-safe availability failure and violates the public promise that ISR context is rejected (`firmware/interface/canview_esp_runtime.h:52-53`).
- Recommendation: reject ISR context before reading task ownership/ticks or modifying runtime/port state. Add direct and BSP-wrapper ISR tests that assert an unchanged runtime and port.

**A-P2-02: pool initialization bypasses its context validator and is accepted from ISR context.**

- Location: `firmware/module/esp_core/pool.c:45-62`
- Failure scenario: an ISR calls `canview_esp_pool_init()` for an uninitialized static pool. The function checks only validator presence, then clears and initializes the pool without invoking `valid_context`.
- Impact: it can mutate pool state without the required task-context contract, race startup, or cause the normal owner’s later initialization to fail busy. This conflicts with the non-ISR pool contract (`firmware/interface/canview_esp_pool.h:3,55-59`).
- Evidence: the candidate ISR test explicitly accepts this behavior at `tests/esp_core/test_runtime.c:323-334`, then tests rejection only for acquire at lines 337-340.
- Recommendation: call `port->valid_context(port->context)` before inspecting/mutating pool lifecycle state; reject non-OK status with no memory change. Replace the ISR test expectation with rejection and verify `initialized == false`.
