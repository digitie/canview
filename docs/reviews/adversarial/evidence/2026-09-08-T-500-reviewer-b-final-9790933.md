**Finding B09-01 — P2: Valid Unicode characters break writer/reader agreement**

Location: [events.py:162](F:/dev/canview-wt/t500-hil/tests/hil/events.py:162), with serialization at line 25.

`EventLog` serializes strings with `ensure_ascii=False`. The reader subsequently uses `str.splitlines()`, which treats U+0085, U+2028, and U+2029 inside those JSON strings as record separators.

Consequently, accepted scenario input produces JSONL that the harness’s own validator rejects, without any evidence modification.

Reproduction used this custom scenario:

```json
{
  "schema_version": 1,
  "id": "unicode-negative",
  "title": "negative",
  "suites": ["host"],
  "mode": "CAPTURE_ONLY",
  "actions": [
    {
      "type": "event",
      "kind": "CAN_TX",
      "fields": {
        "arbitration_id": 291,
        "note": "a\u2028b"
      }
    }
  ],
  "expect": {}
}
```


Independent variants using U+0085 and U+2029 reproduced the same rejection. Plain ASCII and Korean text round-tripped successfully.

Impact: valid Unicode event content makes unedited, runner-produced negative evidence unverifiable. This is an evidence interoperability failure; no false physical PASS or vehicle transmission was demonstrated.

Recommendation: split JSONL using its byte-level LF framing, decode each record as UTF-8, and preserve the existing size, offset, blank-line, and final-newline checks. Add writer-to-validator regressions for all three Unicode separators.
