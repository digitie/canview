## Findings

### P1 — F-01: SDKCONFIG gate가 fail-closed가 아니며 보안·메모리 설정 drift를 허용함

- 위치: \`tools/check_sdkconfig.py:64\`, \`tools/check_sdkconfig.py:84-86\`
- 관련 생성 설정: \`tools/generate_boards.py:158-160\`

\`parse()\`는 \`CONFIG_*\` 값을 모두 읽지만, \`validate()\`는 \`REQUIRED | MEMORY[board]\`와 제한 목록만 검사한다. 그 외 active 설정은 허용되며, 금지 설정도 누락되면 \`"n"\`으로 간주한다.

Candidate object에서 독립 fixture를 사용한 실제 mutation 결과:

\`\`\`text
valid_bridge: ACCEPT
missing_nvs_encryption: ACCEPT
explicit_nvs_disabled: ACCEPT
extra_4mb_flash_selector: ACCEPT
extra_usb_cdc: ACCEPT
secure_boot_v2_variant: ACCEPT
forbidden_octal: REJECT
wrong_flash_16: REJECT
malformed: REJECT
duplicate: REJECT
\`\`\`

특히 generator는 \`CONFIG_NVS_ENCRYPTION=y\`를 출력하지만, gate는 해당 설정을 required로 검사하지 않는다. 따라서 다음도 통과한다.

\`\`\`text
# CONFIG_NVS_ENCRYPTION is not set
\`\`\`

영향:

- Bridge의 encrypted NVS layout과 실제 NVS encryption 설정이 불일치해도 실제 \`sdkconfig\` gate를 통과할 수 있다.
- 검토되지 않은 Flash selector, USB console, secure-boot variant 등이 active여도 gate가 이를 거부하지 않는다.
- \`.config\`가 truncation되어 금지 설정의 \`y\` 라인이 사라져도 누락을 안전한 \`n\`으로 처리한다.
- 차량 CAN TX 경로는 이 task에서 연결되지 않았지만, bench image qualification과 security/evidence integrity를 훼손한다.

권고:

- pinned ESP-IDF 버전별 허용 key 집합을 정의하고 active unknown key를 모두 거부한다.
- \`CONFIG_NVS_ENCRYPTION=y\`를 required로 추가한다.
- 모든 Flash-size selector, console selector, security selector를 명시적으로 검증한다.
- 금지 key 누락을 안전으로 간주하지 말고, actual IDF-generated config와 defaults를 함께 검증한다.
- unknown active key, NVS disabled/missing, forbidden-line deletion, 모든 alternate Flash selector를 독립 mutation test로 추가한다.

### P2 — F-02: Board generator가 USB pin/net/package semantics를 검증하지 않음

- 위치: \`tools/generate_boards.py:96-115\`
- USB fallback: \`tools/generate_boards.py:108-110\`
- Bridge required nets: \`firmware/boards/boards.json:81-84\`

Bridge manifest의 \`required_nets\`에는 \`PAIR_BUTTON_N\`, \`STATUS_LED\`만 있고 \`USB_DM\`, \`USB_DP\`가 없다. \`pin_name\`이 \`USB_D-\` 또는 \`USB_D+\`일 때만 19/20으로 변환하며, 그 이름이 바뀌어도 오류가 발생하지 않는다.

실제 candidate-object mutation 결과:

\`\`\`text
usb_pin_mutation=ACCEPT
#define CANVIEW_BOARD_USB_DM_GPIO (6U)
#define CANVIEW_BOARD_USB_DP_GPIO (20U)

usb_net_mutation=ACCEPT
#define CANVIEW_BOARD_USB_DM_BAD_GPIO (19U)
#define CANVIEW_BOARD_USB_DP_GPIO (20U)

usb_package_pin_13_to_99: ACCEPT
usb_electrical_type_bidirectional_to_power: ACCEPT
\`\`\`

즉, USB D-의 \`pin_name\`을 \`IO6\`으로 바꿔도 generator는 통과하고, generated header는 GPIO6을 산출한다. 그러나 project의 USB Serial/JTAG 설정과 기존 USB pin contract는 19/20을 사용한다.

영향:

- pinmap source와 SDK USB configuration이 서로 다른 물리 핀을 가리킬 수 있다.
- USB diagnostic console이 동작하지 않거나, board evidence가 실제 package/pin 연결을 잘못 나타낼 수 있다.
- 현재 Bridge core는 USB macro를 직접 사용하지 않아 차량 TX 영향은 없지만, generated artifact와 hardware evidence integrity가 훼손된다.
- package pin 번호와 electrical type을 바꿔도 동일하게 통과한다.

권고:

- \`USB_DM\`, \`USB_DP\`를 관련 board의 \`required_nets\`에 포함한다.
- exact net, \`pin_name\`, expected GPIO 19/20을 검증한다.
- package pin 번호와 \`electrical_type\`도 board contract로 고정하거나, generator 입력에서 해당 필드를 제거해 evidence로 오인되지 않게 한다.
- USB pin/net/package/electrical-type mutation test를 추가한다.

### P2 — F-03: 실제 app + Bridge BSP + SDK adapter의 통합 실행 fixture가 없음

- 위치: \`CMakeLists.txt:41-54\`

- \`*-app-tests\`: \`test_app.c\`와 \`firmware/app/esp_core.c\`만 링크하며, \`test_app.c\`가 \`canview_board_port()\`와 \`canview_esp_board_runtime()\`을 fake로 정의한다.

권고:
