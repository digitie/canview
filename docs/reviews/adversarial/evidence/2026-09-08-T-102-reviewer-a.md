## Findings

### P1-001 — diagnostic record가 reset reason을 직렬화하지 않음

위치: `firmware/communicator/stm32/module/diagnostic.c:81-93`

`canview_stm_diagnostic_t`에는 `reset_reason`가 있지만 40-byte record에는 `reset_flags`만 기록되고 `reset_reason`는 기록되지 않는다. `WATCHDOG`, `BROWNOUT`, `AMBIGUOUS` 분류 결과가 UART record에서 보존되지 않는다.

영향:

- T-104 수신자는 STM32-specific reset flag 해석을 다시 구현해야 한다.
- composite/unknown reset 원인의 분류 정보가 유실된다.
- T-102의 reset diagnostic 계약을 충족하지 않는다.

권고:

- fixed record에 명시적인 little-endian `reset_reason` 필드를 추가한다.
- record version/layout을 갱신하고 모든 reset reason 및 ambiguous case를 golden test로 검증한다.
- 현재 `test_platform.c:267-286`에는 reset reason 검증이 없다.

### P1-002 — IWDG 준비 전 HardFault가 bounded reset 없이 영구 대기함

위치: `firmware/communicator/stm32/platform/stm32g474/core_hw.c:411-417`

IWDG가 아직 시작되지 않은 상태에서 HardFault가 발생하면 `__WFI()` 무한 루프에 들어간다. `NVIC_SystemReset()` 호출이나 독립 reset 경로가 없다.

실패 시나리오:

1. safe GPIO 또는 watchdog 초기화 중 HardFault 발생
2. `hardware.watchdog_ready == false`
3. HardFault handler가 영구 대기
4. 외부 reset/watchdog 동작은 physical evidence가 없어 보장되지 않음

영향:

- 초기 부팅 fault가 bounded recovery로 수렴하지 않을 수 있다.
- 외부 gate는 안전 상태일 수 있지만 MCU fault recovery는 보장되지 않는다.

권고:

- IWDG 미준비 상태에서는 명시적으로 system reset을 요청한다.
- 이후 physical supervisor/watchdog reset 경로를 HIL로 검증한다.

### P2-001 — clock/timer fault가 health API 자체에서 terminal latch되지 않음

위치: `firmware/communicator/stm32/platform/stm32g474/core_hw.c:337-345`, `377-387`

HSE/PLL/SWS/TIM2 fault 시 `canview_stm_board_health()`는 `CANVIEW_TIMEOUT`만 반환하고 `hardware.fault`를 latch하지 않는다. 현재 main scheduler 경로는 callback 오류를 받아 별도로 fault를 latch하지만, `canview_stm_watchdog_feed()` 또는 향후 직접 호출자는 fault가 복구되면 다시 feed할 수 있다.

영향:

- terminal clock-failure 계약이 scheduler composition에 의존한다.
- alternate caller가 일시적 clock fault 뒤 watchdog servicing을 재개할 수 있다.

권고:

- 모든 hardware readiness/timebase failure에서 `hardware.fault = true`를 먼저 설정한다.
- scheduler fault latch는 보조 경로로 유지한다.

### P2-002 — module이 BSP/generated header와 protocol header에 직접 의존함

위치:

- `firmware/communicator/stm32/module/build_metadata.c:3-5`
- `firmware/communicator/stm32/module/CMakeLists.txt:9-13`

`module/`의 build metadata가 `board_pins.h`, protocol headers를 직접 include하며 module target에 BSP/protocol include directory가 추가되어 있다. 현재 architecture 계약의 `APP → MODULE → INTERFACE → BSP → PLATFORM` 방향과 module의 interface-only 원칙을 위반한다.

영향:

- module이 board generation과 protocol schema에 강결합된다.
- 다른 STM32 board/profile 또는 host fixture 재사용성이 떨어진다.
- 생성 header와 business module 경계가 흐려진다.

권고:

- metadata assembly를 BSP/platform adapter 또는 별도 provenance interface target으로 이동한다.
- module에는 명시적 metadata provider interface만 노출한다.

### P3-001 — fixed-width 정수 coding rule 위반

위치:

- `firmware/communicator/stm32/module/diagnostic.c:21-23`
- `firmware/communicator/stm32/module/service_policy.c:27-29`

enum 검증에 bare `int`를 사용한다.

영향:

- 현재 값 범위에서는 기능 영향이 없지만 embedded C coding 계약과 이식성 규칙을 위반한다.

권고:

- `int32_t` 기반 검증 또는 enum 범위 전용 helper를 사용한다.
